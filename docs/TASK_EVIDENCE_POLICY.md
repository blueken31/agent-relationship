# 任务证据策略：可选原型与合成验证

状态：`0.7.0.dev0` 开发原型，尚未发布。策略名为 `task_evidence_v1`，默认仍为
`legacy`。目标是让可核验的任务协作事实决定具体问题的处理，保留关系评估作为
独立线索，减少仅因无法量化双方收益而产生的待办。

## 本轮判断

普通评审的双方影响可能无法量化，而具体任务失败、缺少必需检查和目标违规
需要分别处理。未知评估直接成为待办会增加操作；公开合成用例用来检查这些
状态是否被正确区分。机制验证与证明额外诊断价值是两项不同的验收。

本轮只实现问题生成、限定关闭和任务卡片投影，不扩展编排、全局 Agent 配置、
集群因果归因或生产部署。

| 观察 | 新策略行为 | 使用者看到的结果 |
|---|---|---|
| 正常评审、影响无法量化，未声明必需证据缺口 | 保留未知评估和原事件，不创建 `evidence_needed` | 可展开查看记录，不因未知本身要求恢复操作 |
| 已记录失败、错误或超时 | 保留 `task_failure`；与 Agent 归责分开 | 显示原任务失败及一次限定复测建议 |
| 宿主声明下一步缺少必需证据 | 按动作、产出和版本创建 `evidence_needed` | 显示需要核验的具体条件 |
| 目标违规、显著损害或已判定的协作风险 | 继续保留相应问题 | 客观测试通过不能关闭这些语义问题 |
| 匹配预登记条件的新宿主回执 | 可显式关闭对应客观问题，评估可仍未知 | 核对回执 → 关闭本次问题 → 返回原任务 |

“暂无需处理的任务问题”只描述已记录的观察，不能推导出整体健康、目标已达成
或已获执行权限。`can_cooperate()` 的评分与未知处理未改；宿主不能把它的
`can=False` 机械转换为必须暂停。具体原任务是否继续仍由宿主判断。

## 开启与运行

```python
from agent_relationship import RelationshipTracker

tracker = RelationshipTracker(
    llm=None,
    diagnosis_policy="task_evidence_v1",
    storage_path="task-evidence.sqlite3",  # 新检查点，不覆盖旧 legacy 文件
)
```

`llm=None` 不请求语义评估，来源为 `not_requested`，状态为 `unknown`。
不会产生模拟分数，也不会因客观检查通过而提高信任分数。传入现有模型后端时，
仍按现有接口逐事件评估；“只对疑难语义按需调用模型”的路由尚未实现。

运行公开 API 的合成示例：

```bash
PYTHONPATH=. python examples/task_evidence.py
python -m unittest discover -s agent_relationship/tests -q
```

示例中的授权、检查和回执均明确为模拟；真实接入必须使用宿主验证器生成的
实际证据。SDK 不执行检查，也不获取或认证回执。

## 结构化条件与关闭契约

以下字段位于 `track()` 的事件字典中，均要求非空 `task_id`。条件中的字段严格
校验；检查列表须非空、无重复。格式错误会在模型评估和状态修改前报错。

| 字段 | 必填内容 | 含义 |
|---|---|---|
| `failure_condition` | `artifact_id`, `check_ids` | 原问题的产出与失败检查；事件 `result` 必须为 `failed/error/timeout` |
| `evidence_requirement` | `next_action`, `artifact_id`, `artifact_revision`, `check_ids` | 宿主明确声明：此版本的下一动作缺少这些必需检查 |

一次事件只能声明上述一种条件。普通事件可以没有这些字段。SDK 不会仅凭叙述
自动提取必需检查；接入方应将具体评审发现、工具失败或证据缺口映射为结构化
事实。只接入自由文本且关闭语义评估，会漏掉未被映射的语义问题。

`propose_repair(..., verification_contract=...)` 可登记以下完整字典：

```python
{
    "artifact_id": "report",
    "artifact_revision": "sha256:<immutable-artifact-identity>",
    "check_ids": ["boundary-check", "version-check"],
    "verifier_id": "host-checker",
}
```

- 仅适用于 `task_failure` 或 `evidence_needed`，动作限于 `verify_handoff` 和
  `restricted_retest`；`reassign_task` 没有此关闭路径。
- 原问题必须已有结构化条件，契约须涵盖其全部检查。同一产出的多个失败会
  汇总检查要求；不同产出分别保留。缺证据问题还按动作和版本隔离。
- 失败可在修订后的产出上复测，因此契约绑定要验证的目标版本；缺证据问题
  必须验证原先明确要求的同一版本，不能用其他版本的通过结果替代。
- 活跃计划的契约不可替换；需先取消再准备新计划。取消已开始的尝试仍有原有
  冷却限制。开始计划时再次检查新增条件；过时计划仍可读取、重开和取消。
- 未传契约的计划继续采用原来的评估关闭条件；未结构化的历史失败不会被
  悄悄转换为可凭任意通过回执关闭的问题。

宿主授权后执行检查。新的验证事件须携带原 `task_id`、同一 Agent 对、计划
`action`、`repair_plan_id`，以及 `result="success"`、严格布尔值
`verification_passed=True`。还须包含完整 `verification`：

| 验证字段 | 校验规则 |
|---|---|
| `artifact_id`, `artifact_revision`, `verifier_id` | 与计划契约完全一致 |
| `receipt_id` | 非空的宿主回执标识 |
| `checks` | 键与契约检查集合完全一致，每项值为字面字符串 `passed` |
| `started_at`, `finished_at` | 有限数值时间；计划开始 ≤ 检查开始 ≤ 检查结束 ≤ 事件记录时间 |
| `evidence_refs` | 非空、不重复的证据引用列表 |

最终调用 `complete_repair()` 才关闭问题，展示卡片或记录通过回执不会自动关闭。
检查开始时间和事件接收顺序都要满足条件，旧检查延迟送达不能变成新验证。
原问题在执行中新增证据，或同一任务、同一参与者对在计划开始至关闭之间出现
目标违规、显著损害、协作风险，都会阻止该旧计划关闭。关闭以后出现的新问题
保留为后续问题，不改写先前结论。关闭一个问题不清除其他待办。

标识匹配不是身份认证。产出哈希、验证者身份、检查真实性及证据时效必须由
宿主保护；SDK 只检查收到的声明相互一致，不提供防伪签名或跨系统原子保证。

## 体验过程

1. 宿主记录事实；使用者留在原任务，看一条具体问题和一个下一步建议。
2. 普通评估未知保留在展开的依据中，不单独增加待办。不同版本或动作的必需
   检查缺口分别保留，不用一个宽泛的“关系风险”代替。
3. 宿主准备限定验证条件并按自己的权限执行。卡片显示等待原执行结果；重开
   页面不创建新计划或重复执行。
4. 新回执匹配后，下一步为“核对回执并关闭本次问题”；如果宿主报告通过但
   版本或检查不匹配，显示“核对未满足的验证条件”。未知评估仍可见。
5. 显式关闭后显示“本次问题已按登记条件核验关闭”和“返回原任务”。原任务
   后续执行、发布和完成状态继续由宿主管理。

本轮已实现 SDK 任务卡片的数据投影。尚未接入生产宿主页面，也未修改
原有 legacy HTML 预览；新体验的真实使用者验收仍待进行。

## 公开验证范围

公开分发仅包含 SDK 代码、通用说明及明确标注的合成示例和测试。项目名称、
原始日志、业务源码补丁、真实会话、回执、产出哈希和试验报告均不作为公开
测试输入。项目证据在仓库外保管，公开 CI 不读取或上传它们。

合成示例展示“明确失败 → 未量化的评审观察 → 事先登记验证条件 → 模拟匹配
回执 → 显式关闭”的流程。所有授权和检查均为模拟，不把合成通过率表述为
实际项目质量改善。真实诊断价值和使用者体验仍需独立验收。

## 兼容性与下一步验收

默认 `legacy` 的 schema 1 和旧规则保持不变。新策略使用 schema 2，将策略、
契约和计划的提议/开始/完成事件序列一起保存。策略或格式不匹配时拒绝加载并
保留文件，不自动迁移、重算或清空旧数据；试用时创建独立检查点。

本地 Python 3.12.14 验证：347 项公开测试通过。项目证据审计留在非公开验证
环境；旧 HTML 预览和合成示例的可复现性仍属于公开验收范围。
覆盖错误版本/检查/验证者、过期回执、错误任务/参与者/计划、执行后新增风险、
不同下一动作的独立缺口、取消、重启和旧格式兼容。本地结果不代表远程 CI
或 Python 3.10–3.13 全矩阵已经运行。

当前标准模型提示及解析器仍使用双边影响评估契约。进一步把目标/约束判断与
收益打分分开、增加按需语义评估，以及依赖和交接的结构化诊断，均为后续工作。
两两关系分数和低分连通区域仍不能证明集群根因。

下一轮应先接入一个新任务，在执行前提供产出版本和检查契约，再对照：完整
原生 harness、相同 harness 加 SDK 规则、之后的规则加按需语义评估。三种方案
共享事实、正常诊断能力和总预算，不削弱原生组。优先测误报/漏报、错误归责、
无效待办、实际人工介入和恢复时间；保存总用量再谈成本。没有新问题发现或
操作改善时，应如实保留“额外价值尚未证明”的结论。
